# Переезд на сервер

## Граница текущего прототипа

GitHub Pages обслуживает статические файлы. В этой версии нет серверной авторизации, общего хранилища, реальных интеграций или вызовов Claude. localStorage принадлежит конкретному браузеру, может очищаться и редактироваться пользователем. Демо-цифры нельзя принимать за данные компании. Сохраняемые локально изменения нужны только для проверки сценариев.

## План переноса

1. Реализовать сервер по контракту API.md и базу с версиями схемы. Предлагаемая структура: owners, directions, products, variants, stock_balances, locations, handling_units, receipts, receipt_lines, operations, employees, shifts, pay_rates, payroll_accruals, service_rates, service_accruals, expenses, receivables, payables, audit_events.
2. Все приёмки и движения выполнять серверными транзакциями. Уникальные идентификаторы источников и ключи идемпотентности предотвращают дубли. Использовать блокировки/оптимистические версии для конфликтующих действий. Проверять неотрицательные доступные остатки.
3. Перенести расчёты domain.js на сервер или воспроизвести их с теми же контрактными тестами. Авторитетные суммы и ставки определяет сервер; клиент передаёт только намерение операции. Деньги хранить целыми копейками или DECIMAL, без накопления ошибок float.
4. Добавить учётные записи, роли, ограничения по владельцам и направлениям. Сервер проверяет доступ на каждом endpoint. Использовать защищённые HttpOnly session cookie, CSRF-защиту и аудит; не подменять авторизацию выбором роли на клиенте.
5. Добавить вход и выход в интерфейс. HTTP-адаптер пока только сообщает 401; полноценного login flow в v0.1 нет.
6. Разместить корень сайта за HTTPS reverse proxy. Маршрут /api/v1 направить на backend. Можно сначала оставить frontend на Pages и подключить отдельный API, но для cookie/CORS понадобится отдельная конфигурация доверенного origin.
7. В config.js установить `dataMode: 'api'`, `apiBaseUrl: '/api/v1'` после готовности backend. Заменить фиксированный демо-период, DEMO_DATE и демо-подписи на диапазоны и актуальную дату сервера; добавить состояния загрузки и постраничную загрузку для больших таблиц.
8. Подключить 1С и самописную БД через отдельные интеграционные задания: инкрементальная загрузка, идентификаторы источника, повторы, сверка и журнал ошибок. Не давать браузеру прямой доступ к БД.
9. Добавить серверный endpoint аналитического чата. Ключ Anthropic хранить в секретах сервера; разрешённые отчёты выбирать с учётом прав пользователя. Ответы содержат источники и время среза. Отправляемые Claude данные согласовать по составу, исключать лишние персональные данные.
10. Провести пилот приёмки ФФ: параллельная сверка остатков, начислений и журналов, резервное копирование и тест восстановления. После проверки включать остальные направления.

## Что остаётся пригодным

Разметка, стили, разделы, формы и repository boundary сохраняются. Для промышленной версии нужно развить сервер и клиентский слой данных, а не просто заменить место размещения. Целиком загружаемый snapshot подходит для прототипа; на больших объёмах нужны отдельные paginated endpoints и серверные агрегаты.

## Данные и тарифы

Ставка хранится снимком в операции. Реальная система должна версионировать тарифы по дате действия, сохранять закрытые периоды и проводить исправления отдельными событиями. Операции клиента ФФ и собственного производства не смешиваются. Внутренние начисления исключаются из консолидированного дохода. Хранение начисляется по интервалам присутствия товара, а не текущему остатку.

## Нагрузка и целостность

Требование 5–8 тысяч товаров в день сначала уточнить в единицах измерения. Локальная демо-реализация не обеспечивает конкурентные транзакции между сотрудниками, защиту от подмены, резервирование запасов и гарантированную сохранность. Серверный пилот должен проверять эти свойства отдельно.
